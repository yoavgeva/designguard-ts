# Spike: can an ESLint plugin follow calls across files? (2026-10-31)

Question: does typescript-eslint's program resolve enough calls, fast enough, for rules that follow calls across
files? The bar was at least 75% of calls resolved, and lint time no more than twice typescript-eslint's typed rules
alone.

## Method

- **Apps and versions.**
  - Immich server: NestJS and Kysely, commit 3184b15.
  - openstatus: Hono and Drizzle, f8057fb.
  - Cal.com: tRPC, Prisma with the `prisma-client` generator, and the NestJS API v2, a5ee96f.
  - Vendure core: NestJS and TypeORM, 3ef5fbe. Its `@vendure/common` package was built first.
  - Twenty didn't install: Yarn exits during its fetch step without an error.
- **Setup.** Each app was installed with lifecycle scripts disabled, in a Docker container capped at 2 GB.
- **Tools.** ESLint 10.14, typescript-eslint 8.72 and TypeScript 5.9.3.
- **Runs.** Each app was linted three times with the same files:
  - **A:** `no-floating-promises`, `no-misused-promises` and `await-thenable` alone;
  - **B:** A plus `designguard/no-queries-in-loops`;
  - **C:** B plus resolution statistics, which resolve every call, so they're kept out of B's time.

## Results

| App, package | Calls | Resolved | `any` | Abstract | A | B |
|---|---|---|---|---|---|---|
| Immich server | 57,779 | 99.1% | 85 | 435 | 19.0 s | 19.1 s |
| openstatus | 30,545 | 99.5% | 52 | 109 | out of memory | out of memory |
| Cal.com API v2 | 24,813 | 99.5% | 98 | 21 | out of memory | out of memory |
| Cal.com features | 13,047 | 96.6% | 153 | 288 | out of memory | out of memory |
| Cal.com lib | 6,500 | 98.6% | 65 | 27 | 4.5 s | 4.7 s |
| Cal.com tRPC server | 4,733 | 96.0% | 184 | 4 | 13.0 s | 10.5 s |
| Vendure core | — | — | — | — | 9.3 s | 8.8 s |

- **Out of memory.** These runs ran out in A too: typescript-eslint itself needs more than 2 GB for those projects.
- **Vendure's statistics.** Run C ran out of memory before writing them. Before `@vendure/common` was built, 80.9%
  of its calls resolved; the rest went through `any` because the built package was missing.

Changes the spike led to:
- **Generated code.** Prisma's `prisma-client` generator writes the client into the project, so adapters claim
  files with `files` patterns.
- **Polling loops.** `while` loops aren't per-item loops.
- **Caching.** typescript-eslint's project service builds several programs per run, so summaries are cached per
  source file.
- **On-demand resolution.** Resolving every call up front cost 2.6 times A on Vendure. Resolving on demand (a file's
  loop calls, and what they reach) brought B to within noise of A.

## Decision

Go: resolution is 96–99.5% and lint time about 1×.
